# Orchestrator state: issue body template

Copy everything below the line into the state issue body (label `orchestrator-state`). Rules:
[`ORCHESTRATION.md`](ORCHESTRATION.md) §3. Only the active orchestrator edits it. The body has three parts:

1. **Prose**: the two sentences below and, when needed, short free text for the owner. Nothing in it is read by a script.
2. **Generated summary**, between the two `state:summary` markers. Never edit it by hand: edit the block and run
   `scripts/state_body.py render body.md > new.md`.
3. **One fenced `json` block**, the state itself (schema 1, checked by `scripts/state_body.py validate`). Every field is mandatory
   (only a session row's `note` is optional); unknown, missing or wrongly typed fields fail the check. `tasks.py --state` reads the claimed
   and in-review task ids from this block (§4.3).

Read, edit, check, write (every wake that changes state):

```bash
gh api repos/{owner}/{repo}/issues/<state issue> --jq .body > state.md   # the current state issue, ORCHESTRATION.md §3.4
# ... edit the block in state.md (and the prose) ...
python3 -I scripts/state_body.py render state.md > new.md                 # regenerates the summary, canonical block
python3 -I scripts/state_body.py validate --comments "$(gh api repos/{owner}/{repo}/issues/<state issue> --jq .comments)" new.md
gh api -X PATCH repos/{owner}/{repo}/issues/<state issue> -F body=@new.md
```

`validate` exits 1 with every problem on stderr (do not write a body that fails). A valid body prints `ok: ...` and, when the body is
15000 bytes or more or the issue has 250 or more comments, one `rotate:` line (ORCHESTRATION.md §3.5): rotate at the next handover boundary.
Keep the whole body under that limit: history goes into comments or onto the PR concerned, not into the body.

Field notes (the schema in `scripts/state_body.py` wins):
* Times are UTC, `2026-11-23T05:33Z`. `usage.state` is one of the §3.1 states. `tasks_ref` is the one ref that carries `docs/tasks.toml`
  (the ready query reads it from here, §4.3).
* `sessions[].tasks` are the claims; release them (empty list) when a row is `archived` or `failed`. `branches[].in_review` are the tasks
  awaiting review or merge. A task id appears in at most one session row.
* `owner_queue[].kind` is `todo`, `question` or `approval`; `then` is the orchestrator's follow-up action.
* `follow_ups` is the count line of `tasks.py followups`; `open` is the sum of the four severities.
* `next` has 1 to 3 concrete actions a cold successor can take. Re-schedule the 45-minute check-in on every wake (§1.1).
* `decisions` lists the standing owner decisions (comment id and a few words); a new issue after a rotation carries them over once.

## Comments on the state issue (owner decision 7076085601 item 1)

Comments only for: `decision`, `batch approval:` records and `veto #N`, `handover`, `handover-ack`, `handover-released`, `takeover`,
`lock-lost`, `incident`, `PAUSED` / `RESUMED`, `metrics:*` blocks (§6) and the weekly digest. Progress, check-ins and "no change" wakes
go to the body (`updated` in the block) or onto the PR concerned, never into a comment. Metrics rows are batched into the next decision
or metrics comment, or one metrics comment per check-in with no prose. The older log kinds (`correction`, `todo-done`) are retired:
fix the body and say so in `updated.after`. Open questions for the owner go into the block's `owner_queue` (kind `question`, with
the recommendation in `text`) and, when the owner has to read them first, the prose above the summary.
