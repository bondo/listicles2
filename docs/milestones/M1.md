# M1 plan: accounts and households

Status: working draft (task M1-01, 2026-11-17); not owner-approved (see issue #15).

Inputs: `docs/PLAN.md` sections 3 to 3.4 and 7 (as updated by the OQ-15 PLAN update PR), `docs/product/stories.md`
and `flow.md` (working drafts: parts the owner has not confirmed are marked below), `docs/ANDROID-BEST-PRACTICES.md`
(approved), and the owner decisions on issue #15 up to 2026-11-17. Facts about Firebase and Android are cited to
official pages fetched on 2026-11-17.

**Done when** (PLAN section 7): two verified emulator users (one Google, one password) join one household; an
unverified user and an outsider are denied (rules allow and deny tests); the M1 stories below have acceptance tests.

**Stories in M1:** AUTH-01..11, HH-01..06, LANG-01/02 (LocaleConfig), SYNC-03 for the actions above. Lists and items
(LIST, ITEM, VIS, SYNC-01/02) are M2; M1 rules and batches leave room for them (PLAN 3.1: leave, remove and delete
household also unshare lists; those list writes are added in M2, when lists exist).

## 1. Ground rules for every M1 PR

* One concern per PR, about 400 changed lines or fewer; the guard fails at 600 (docs count).
* Test-first: the first commit adds failing tests (negative cases included); the commit order shows it.
* `risk:high` (PLAN 9.1): security rules, auth flows that decide who is signed in, account deletion, household
  batches. Implementer at high effort, reviewer at max effort. Rules PRs need allow **and** deny tests in
  `firebase/test` for every rule they touch.
* Android guidance: cite `docs/ANDROID-BEST-PRACTICES.md`; UI, domain and data layers; state hoisting; fakes over mocks.
* Strings in `values/` and `values-da/` (Danish "ting" for item, "Jeg har den" for "I have it", "Genudgivelsesår").
* Firebase and Google artifacts are licence-approved one by one when first added (M0.5 licence check, owner D3):
  each PR that adds one names it, and the owner approves it in that PR.
* No real `google-services.json` in the repo or in CI: CI and the emulator use the `demo-` project. The first PR that
  needs the Google Services Gradle plugin also adds a CI-only stand-in config with dummy values, generated at
  build time, never committed (risk to check in that PR: the plugin's validation).

## 3. Owner steps (admin, no code)

Order matters: R1 before any PR that talks to a real project; none of the PRs needs a real project for its tests.

**R0. Rename first (before R1).** The Firebase Android app is registered with the package name, so M1-29 (rename to
`dk.bjarkebjarke.tally`, `docs/product/naming.md`) merges before R1.

**R1. Firebase project and database** (task M1-O1).
1. Create the Firebase project (Spark), named for Tally; no Google Analytics (decided: Crashlytics only).
2. Firestore: create the database in **`eur3`** (Belgium and the Netherlands). The location cannot be changed
   later[^loc]. Start in production mode (everything denied) until the rules from `firebase/firestore.rules` are
   deployed by hand (`firebase deploy --only firestore:rules`; CI never deploys).
3. Authentication: enable Google and Email/Password; check that email enumeration protection is on (default for
   projects created after 15 September 2023[^enum]); password policy: Require mode, minimum length 12[^pw].
4. Email templates (verification, password reset): English and Danish texts (OQ-29); default Firebase action pages.
5. Register the Android app `dk.bjarkebjarke.tally`; add `google-services.json` as a GitHub secret (not used by CI tests).

**R2. Optional TOTP** (task M1-O3; needed before M1-23).
1. Check in the console that the Identity Platform upgrade asks for no billing account (OQ-25). If it does, stop:
   AUTH-09 is dropped from v1 and M1-23 is marked dropped.
2. Upgrade, then enable TOTP once with the REST call from the Firebase page[^totp] (run locally with `gcloud`; MFA
   also needs verified emails, which v1 requires anyway):
   `curl -X PATCH "https://identitytoolkit.googleapis.com/admin/v2/projects/PROJECT_ID/config?updateMask=mfa"`
   with headers `Authorization: Bearer $(gcloud auth print-access-token)`, `Content-Type: application/json`,
   `X-Goog-User-Project: PROJECT_ID` and the body
   `{"mfa":{"providerConfigs":[{"state":"ENABLED","totpProviderConfig":{"adjacentIntervals":5}}]}}`.

**R3. MFA reset runbook** (lost authenticator, OQ-28; no code in the repo).
1. Confirm the person's identity outside the app (they write from the account's email address).
2. With the Admin SDK for Node, run once from your own machine, authenticated with
   `gcloud auth application-default login` (no service-account key file):
   `getAuth().updateUser(uid, { multiFactor: { enrolledFactors: null } })`[^mfa].
3. Tell the person to sign in and, if they want, turn two-step verification on again. Note the reset on issue #15
   without the email address.

**R4. Signing fingerprints** (task M1-O2): SHA-1 and SHA-256 of the debug key now, of the owner-held GitHub
release key when it is made (M6), in Firebase (Google sign-in) and App Check.

**R5. App Check** (task M1-O4, after M1-26): register Play Integrity; in the advanced settings require device
integrity and turn off `PLAY_RECOGNIZED` and licensing (default requires `PLAY_RECOGNIZED`[^pi]); add a CI debug
token as a GitHub secret[^acdebug]; watch the metrics for about two weeks before enforcing[^acmon] (enforcing is M6).

**R6. Privacy text** (task M1-O5): approve the M1-28 draft before anyone else installs the app (OQ-30).

## 5. Per-PR notes (acceptance tests, test-first, risks)

**M1-29 Rename.** Test first: a unit test reads `BuildConfig.APPLICATION_ID` and the app label resources (en, da)
and expects `dk.bjarkebjarke.tally` and "Tally". Moves are mostly renames (git counts them as small). The repo
rename is the owner's (issue #15, 2026-11-17) and is not part of this PR.

**M1-08 Rules base (risk:high).** Tests first in `firebase/test`: an anonymous request, an unverified password
token, a verified password token and a Google token (`email_verified: true`) against `users/{uid}` (own: allow;
other: deny; unverified: allow only the own doc, so the app can store nothing else) and the app config document (read: any
verified user; write: nobody). Every later rule uses `signedIn()`; a test helper asserts that each collection
denies an unverified token, so a new rule cannot forget it.

**M1-09 Spike (risk:high).** Emulator tests for PLAN 3.1 items (a) invite `list` with membership `exists()`,
(b) join batch with `existsAfter`/`getAfter`, (c) transfer batch, (d) list query on `sharedWith` with membership
and `LIVE`, (e) the largest batches against the 10/20 access-call limits[^calls]. Output: ADR 0002 records each
result and, if (a) fails, the nested-invites fallback. The tests stay as regression tests; rules written only for
the spike are replaced in M1-10..12.

**M1-10 / M1-11 / M1-12 Rules (risk:high).** One PR each, PLAN 3.1 rows verbatim. Allow and deny tests per row,
including: creating a household while `users/{uid}.householdId` is set (deny); a former creator re-creating a
tombstoned id (deny); transfer that leaves two owners (deny); leave by the owner (deny); removal of the owner in
the same batch as a transfer (deny); any read under a soft-deleted household by a member (deny) and by the
owner's cleanup (allow). M1-12: invite `get` by an **unverified** user (deny; HH-03), by a verified non-member
(allow), enumeration by `list` without the `householdId` filter (deny), join with an expired, revoked or used code
or an invite whose creator left (deny), join that does not delete the invite (deny), an existing member burning
someone else's invite (deny). Rule coverage report from the emulator attached to the PR (investigation item 9).

**M1-30 App skeleton.** Hilt, Navigation 3 (owner decision on the checklist), a root that shows sign-in or the
signed-in home from the auth state, and a `Connectivity` interface with a fake for "This needs a connection"
(SYNC-03). Konsist rules from M0.5 apply. Compose UI test: signed-out start shows the sign-in route.

**M1-13 Validation.** Pure Kotlin in `core/domain`: password length is counted in code points (12 or more, no
other rule, OQ-26), email trimmed and non-empty (Firebase decides validity). Property tests: any string of 12+
code points passes, any shorter fails; whitespace-only email fails.

**M1-14 Google sign-in (risk:high).** Credential Manager with the Google ID option[^gsi], then
`signInWithCredential`. Integration tests against the Auth emulator: a Google-style credential signs in and the
token has `email_verified`; sign out clears the session. Unit tests with a fake `CredentialManager` wrapper for
cancel and no-account cases. OQ-13 (sign out removes local data) is still an assumption: M1 clears the Firestore
cache on sign out only if the owner confirms (section 6).

**M1-15 Email and password (risk:high).** Sign up sends the verification email with `useAppLanguage()`; sign in;
reset; resend verification. Error mapping that reveals nothing (AUTH-10): sign up with an existing email shows the
same "check your email" result and signs nobody in (R3-01); wrong password and unknown email give the same message
(`INVALID_LOGIN_CREDENTIALS` under enumeration protection[^enum]); the non-Gmail collision shows the decided
message. Auth emulator tests for each case, including the reverse case of OQ-34(b) (reset for a Google-only email):
record what the emulator does and check it once in the real project (R1) before relying on it.

**M1-16 / M1-17 Sign-in UI.** Screens from the wireframes (PR #113 when merged; screens 24-33 for password flows),
en/da, light/dark, accessibility checks on (M1-03). Compose tests with fake repositories for every acceptance line
of AUTH-01..03 and AUTH-05..08, AUTH-10, plus the "needs a connection" state (SYNC-03).

**M1-24 LocaleConfig.** `androidResources { generateLocaleConfig = true }` and `res/resources.properties` with
`unqualifiedResLocale=en`[^lang]. Test first: a JVM test over the merged resources (or the AGP-generated
`locale_config.xml`) expects exactly `en` and `da`. No in-app picker (OQ-12).

**M1-18 Household data (risk:high).** One repository, batches exactly as PLAN 3.1; integration tests against the
Firestore emulator with two and three users: join, leave, remove, transfer, delete; a crash between soft delete
and cleanup resumes on the next start; expired invites are cleaned when the household screen opens.

**M1-19 / M1-20 / M1-21 Household UI.** HH-01..06 acceptance lines as Compose tests with fakes. M1-20: the link
format and the web page for "install, then tap the link again" depend on the owner's domain (OQ-21, hosting
undecided): until then the link uses the domain path without App Links verification and the test covers the
intent filter only. HH-06 deletion notice is a dialog the user must acknowledge.

**M1-22 Account (risk:high).** AUTH-11: recent sign-in, new password 12+ (M1-13), old one stops working (Auth
emulator). AUTH-04: the order from PLAN 3.1 (leave or transfer first, then delete own data, then `users/{uid}`,
then the Auth user); re-auth happens before the first write[^reauth], so a failed re-auth leaves nothing
half-done; tests for the owner-with-members guard and for a crash mid-way (resumable).

**M1-23 TOTP (risk:high).** Enrol with a QR code and a code check, second factor at sign-in and at re-auth,
turn off. The warning before enabling never mentions an administrator (OQ-28). Tests against the Auth emulator
where it supports TOTP; otherwise a fake and a manual check on the real project, recorded in the PR. Marked
dropped if R2 step 1 fails.

**M1-25 Crashlytics opt-in.** Manifest `firebase_crashlytics_collection_enabled=false`; a "Send crash reports"
switch (en/da) calls `setCrashlyticsCollectionEnabled`[^crash]; no Analytics dependency (a Gradle test fails if
`firebase-analytics` is on the runtime classpath). Tests: the merged manifest has the flag off; the switch writes
through a fake.

**M1-26 App Check.** Play Integrity provider in release builds, debug provider in debug and CI builds; the debug
token comes from a CI secret, never from the repo. Test: the debug build installs the debug factory (unit test
on the DI module). Enforcement stays off (R5).

**M1-27 Minimum version.** `minVersionCode` in the app config document read at start (cached; offline uses the last value);
below it, a full-screen "Update the app" with the GitHub Releases link. `schemaVersion` written on new lists in M2.

**M1-28 Privacy text (OQ-30).** Danish and English, in a new `privacy` folder under `docs`: who is responsible; Google (Firebase) as
processor of email addresses, passwords and list data; Authentication processed in the US[^authus] and
Firestore stored in the EU (`eur3`); crash reports only after opt-in, no analytics; how to delete the account in
the app and through the web resource (once decided); contact. The owner approves it (R6); it may be linked from
the app's settings in a later PR.

## 6. Owner questions raised by this plan (one at a time, each with a recommendation)

* **OQ-34(c)** Password sign-in for a Google-only email says "Wrong email or password". Add a hint for everyone?
  *Recommendation:* yes: "Wrong email or password. If you signed up with Google, use Continue with Google." It is
  shown on every failure, so it reveals nothing.
* **OQ-34(d)** Sign-up still reports an existing email to someone who calls the API directly[^enum]. Accept?
  *Recommendation:* accept for v1: the app shows the same screen either way (AUTH-10), App Check (M1-26) makes
  scripted calls harder, and dropping password sign-in would undo OQ-23.
* **OQ-34(a), (b)** (a) is decided (the collision message). (b) is checked in M1-15 and once in the real project.
  *Recommendation:* if a reset adds a password to a Google-only account, accept it for v1 (same account, no data
  lost) and say so in the stories.
* **OQ-35** "Most recently used" for LIST-01. *Recommendation:* last **opened by me**, kept on the device only (no
  Firestore writes or reads); lists never opened on this device follow `updatedAt`. Decide before M2 planning.
* **OQ-13** Sign out removes the local copy of the user's data. *Recommendation:* confirm: clear the Firestore
  cache on sign out (`clearPersistence` after `terminate`), so the next person on the phone sees nothing.
* **OQ-38 Backups and export** (deferred to M1 planning). No backups on Spark (they need Blaze[^backup]).
  *Recommendation:* an in-app export of my lists to a JSON or CSV file through the system file picker, in M2 (it
  needs lists), before the first external tester; it also covers data portability. No Blaze.
* **OQ-39 Undo snackbar timing** (deferred to M1 planning; the feature is M2). *Recommendation:* follow Material 3:
  the Undo snackbar stays until the user acts, dismisses it or leaves the list (the delete is already written, so
  nothing waits on it); the 10 s in the wireframes is dropped.
* Reminders, not new: palette T1 (before M1-04), the invite web page domain (OQ-21, before M1-20), the web
  account-deletion page (before the first external tester), OQ-36 and OQ-37 (PLAN update PR).
