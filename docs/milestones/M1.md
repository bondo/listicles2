## 1. Ground rules for every M1 PR

* One concern per PR, about 400 changed lines or fewer; the guard fails at 600 (docs count).
* Test-first: the first commit adds failing tests (negative cases included); the commit order shows it.
* `risk:high`: PLAN 9.1 names security rules, sync and merge logic, and release work; this plan extends it to auth
  flows that decide who is signed in, account deletion and household batches (the owner may narrow this). Effort follows PLAN 9.1 and `agents/roles.yaml`: implementer and reviewer at high effort, max only for the first reviewer of an `area:security-rules` or `area:sync-merge` PR (owner decision 7153510972). A PR that changes `firestore.rules` or its tests also carries `area:security-rules`; one that changes sync, conflict or merge behaviour carries `area:sync-merge` (PLAN 9.1; reviewer at max even without `risk:high`). Rules PRs need allow **and** deny tests in
  `firebase/test` for every rule they touch.
* Android guidance: cite `docs/ANDROID-BEST-PRACTICES.md`; UI, domain and data layers; state hoisting; fakes over mocks.
  Each product PR names the checklist sections it applies (for example 1, 2, 4, 5 and 7 for a screen with a repository).
* Until detekt 2.0 gives Android modules type resolution (#218), reviewers of `:core:data` and `:app` PRs check by
  hand that dispatchers are injected, never hard-coded (`Dispatchers.IO`); checklist section 5.
* Reviews (issue #65; named #65-Rn so they differ from the owner steps R0-R7 of section 3): #65-R1 every PR; #65-R7
  (fresh reviewer, max effort, allow/deny matrix) every `risk:high`,
  `area:security-rules` or `area:sync-merge` PR; #65-R9 (rubric) inside #65-R1 for UI PRs; #65-R12 (M1-47) and #65-R8 (M1-48) at the
  end of M1, before M1-FU. Their findings target M2 (`docs/FOLLOW-UPS.md` section 3).
* Strings in `values/` and `values-da/` (Danish "ting" for item, "Jeg har den" for "I have it", "Genudgivelsesår").
* Firebase and Google artifacts are licence-approved one by one when first added (M0.5 licence check, owner D3):
  each PR that adds one names it, and the owner approves it in that PR.
* No real `google-services.json` in the repo or in CI: CI and the emulator use the `demo-` project. Firebase setup
  has two owners: M1-02 adds the Firebase BoM and the Auth and Firestore libraries to the version catalog and
  `:core:data` (tests initialise Firebase by hand for `demo-tally`, no plugin); M1-30 adds the Google
  Services Gradle plugin to `:app` with a CI-only stand-in config with dummy values, generated at build time and
  never committed (risk to check there: the plugin's validation). Later tasks (M1-66, M1-25, M1-26, M1-27) only
  add their own libraries.

   the Play account, which is deferred; without the link the default quota is 10,000 requests a day and cannot be
   raised[^pisetup], plenty for testers.
2. In Firebase App Check, register the app with the Play Integrity provider; in the advanced settings require
   device integrity and turn off `PLAY_RECOGNIZED` and licensing (the default requires `PLAY_RECOGNIZED`[^pi]).
   Play Integrity only runs in release builds, so the SHA-256 to register is the GitHub release key's, added by
   M6-O1 when that key is made (before the first external tester); the debug key (M3-O2) is not registered here,
   because debug builds use the debug provider.
3. Debug tokens[^acdebug] only for the owner's own debug builds against the real project. CI talks only to the
   emulators, which do not check App Check, so CI needs no token and no secret.
4. Watch the metrics for about two weeks before enforcing[^acmon] (enforcing is M6).

**R6. Privacy text** (task M1-O5): approve the M1-28 draft before anyone else installs the app (OQ-30).

**R7. Deploy the rules** (task M1-O6, #209). CI never deploys. After each merged PR that changes
`firebase/firestore.rules`, and before any tester build, run `firebase deploy --only firestore:rules` from that `main`
commit and note the commit on issue #15. Before each tester build, compare the live ruleset in the console with
`main`; a difference means deploy again before testing.

On a workstation with only Nix (task M1-96: Node from the pinned nixpkgs, firebase-tools 15.36.0 from `firebase/package-lock.json`;
the first run does an `npm ci` in `firebase/`), from a checkout of that merged `main` commit at the repository root. `firebase/.firebaserc`
names only the emulator project (`demo-tally`), so every command names the real project with `--project tally-c1a15`; do not change
`.firebaserc` (no `firebase use`). The deploy runs in `firebase/` (where `firebase.json` is). Log in once with `firebase login` the same way.

* Without flakes (works with the default Nix settings): `nix-shell --run "cd firebase && firebase deploy --only firestore:rules --project tally-c1a15"`
* With flakes: `nix --extra-experimental-features 'nix-command flakes' develop -c bash -c 'cd firebase && firebase deploy --only firestore:rules --project tally-c1a15'`
  (or set `experimental-features = nix-command flakes` in `~/.config/nix/nix.conf` and drop the flag).

Check the version first with `nix-shell --run "firebase --version"` (expect the version in `firebase/package-lock.json`).

## 8. Planner decisions (cheap to reverse, recorded here; the plan reviewer checks each)

Rules decisions (written into PLAN by M1-35, before M1-08; all `risk:high`, `area:security-rules`):
* **P1 (#206)**: in the PLAN notation `uid` is `request.auth.uid`. The member-doc create in Create household and in
  Join requires the doc id to be `request.auth.uid`. Deny tests (M1-10, M1-54): a member doc for another uid in either
  batch, a second member doc in the same batch.
* **P2 (#200)**: `invites/{code}` stores `householdName`; Create invite requires it to equal
  `get(/households/$(householdId)).data.name`. The join screen shows that name, never one from the URL. Tests
  (M1-12): allow a verified non-member with the code to read it; deny an invite whose name differs. Spike (e) counts
  the extra read.
* **P3 (#243, #210 item 3)**: Create household requires the id to match `^[A-Za-z0-9]{20}$` (Firestore's auto-id).
  An invite's id is `<householdId>_<secret>`, the secret 22 characters of `[A-Za-z0-9_-]` from a secure random
  source (132 bits); Create invite requires `code.matches('^[A-Za-z0-9]{20}_[A-Za-z0-9_-]{22}$') && code.split('_')[0] == householdId` (PLAN 3.1, R1-A-01 of PR #265). Deny tests:
  re-creating a deleted code for another household, a short or odd code, a household id that is not an auto-id.
  Accepted residual: a member of the same household can re-create a revoked code of that household; they could send a
  new link anyway.
* **P4 (#203)**: every create checks `keys().hasOnly([...])` and `hasAll([...required])`; every update row checks
  `diff(resource.data).affectedKeys().hasOnly([...])`. Lengths (code points as the app counts them; in the rules
  `matches('(?s).{1,N}')`, because `size()` counts UTF-16 units, #15 comment 7083518706; not blank, as PLAN 3.1 field validation defines it since M1-90: no name of only U+0000 to U+0020 and Unicode White_Space): household name 1-50, `displayName` and `users.name` 1-50. M2 planning sets list and
  item names (proposal: 80 and 200). Tests per collection: an unknown field (deny), a create without one required key
  (deny; at least the owner's member doc without `joinedAt`, M1-10), exactly max (allow), max + 1,
  spaces only and Unicode spaces only (deny), a 50-code-point name with non-BMP characters (allow; M1-13 has the matching property). The same numbers drive the UI field errors (M1-13).
* **P5 (#210)**: (1) the users doc may be deleted only when `householdId == null` (deny with a stale value; account
  deletion self-heals first); (2) `null` → `hid` also needs `getAfter(/households/$(hid)).data.deleted == false`, so a
  user cannot point back at a tombstone; (5) `firestore.indexes.json` is added by the first PR with a composite query
  (M1 has none: the expired-invite queries have equality filters only, `householdId` and, for a plain member,
  `createdBy` (#280), and check expiry on the client); (6) the
  `updatedBy`/`updatedAt` bullet applies to documents that have those fields (lists, items).
* **P6 (#242)**: while `deleted == true`, a member may delete their own `members/{uid}` (nobody else's); the self-heal
  does it before clearing `householdId` (M1-31; M1-18 does not, see section 5). Tests (M1-95): allow own under a tombstone,
  alone and in one batch with the users-doc clear, deny another member's;
  under a live household the Leave row applies unchanged.
* **P7 (#205 item 5)**: in account deletion the last member's household cleanup finishes (all pages) before
  `users/{uid}` and the Auth user are deleted; a crash in between resumes the cleanup first. Test (M1-32): crash after
  the soft delete, restart, then no member doc remains and the account is gone.
* **P8 (#250)**: the removal self-heal moves the name from the app's household-name copy (same `householdId` match as
  HH-06) into the removal-notice state before it deletes the copy. With no usable copy, wireframe 40 uses the approved
  story text without a name: "You were removed from the household" / "Du er fjernet fra husstanden". Tests: M1-18
  (state carries the name, a copy for another household gives none), M1-21 (both texts, en/da).
* **P9 (AUTH-12, new gap: no task stored the name)**: `users/{uid}` holds `householdId` and `name`; `name` may be
  missing (then the start gate shows the name step). The own-doc exception for unverified users stays, so create
  account saves the name before verification. Not the Auth profile `displayName`: Google sign-in fills that in, so
  the app could not tell a confirmed name from Google's. The member doc's `displayName` is a copy, set on create and
  join and changed together with `name` (M1-39).
